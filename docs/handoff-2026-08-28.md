# 2. Intended dual-mode product shape

The product should have two usages:

```text
Desktop mode
SPlayer UI
  → Electron IPC
  → same main playback/session/library services
  → Native audio-engine
  → Diretta / normal output

Headless mode
Browser SPlayer UI
  → HTTP + WebSocket
  → same main playback/session/library services
  → Native audio-engine
```

The browser never decodes or plays audio. The Atom host owns all source resolution, local file access, queue state, Native decoding and Diretta output.

No second daemon is wanted. Production Headless uses the existing Electron main process with no BrowserWindow plus the existing Hono server.

# 5. Main-process authoritative queue / playback session

A major architectural correction was made during this phase.

The first Headless MVP temporarily had:

```text
main playbackSession queue
+
renderer upstream queue
```

That violates `AGENTS.md` “One source of truth”. The implementation was therefore changed so the main process owns the authoritative playback session.

Current Atom-owned session files:

- `electron/main/services/playbackSession.ts`
- `electron/main/database/playbackSession.ts`
- shared snapshot extensions currently in `shared/types/player.ts`

The session owns:

- queue
- originalQueue for shuffle restoration
- current index
- repeat
- shuffle
- current track projection

The renderer queue is intended to become only a reactive projection of main state.

The session currently supports operations including:

- replace
- append
- insert
- update item / track metadata
- remove
- clear
- move
- select index
- next / prev
- repeat
- shuffle / restore original order
- remove streaming-server tracks

Important semantic rule:

- Headless natural `ended/sourceError` can be advanced by main session.
- Desktop still needs renderer orchestration for provider resolution, lyrics, statistics, streaming context, etc.
- Do not let MPRIS/tray/Desktop external Next bypass upstream renderer orchestration for online tracks.

A prior review already caught and fixed that boundary once; preserve it.

## Persistence

Queue/session persistence was moved from renderer IndexedDB toward the same main authoritative session.

A single-row `playback_session` record in the existing `library.db` is the intended persistence store.

No new database service is used.

Legacy renderer `splayer/queue` is only a one-time migration source; after successful migration it should no longer be a second runtime/persistence authority.

During the current touch-budget refactor, the schema creation was moved out of upstream `database/index.ts` into Atom-owned `electron/main/database/playbackSession.ts` so the main database seam is not widened unnecessarily.

# 6. DSD local-library discovery is fixed

Before this phase, Native Direct could play DSF but the SPlayer local scanner ignored DSD files.

That has been fixed in `native/audio-engine/src/scanner.rs`.

Important correctness decision:

Do **not** use FFmpeg’s PCM-oriented DSD representation as library truth.

A real DSD256 file was observed by FFmpeg as approximately:

```text
1,411,200 Hz × 8 bit
```

but Source Direct truth is:

```text
11,289,600 Hz × 1 bit × 2ch
```

The scanner therefore uses `DirectDsdReader` as the authoritative source for native DSD:

- one-bit rate
- channels
- 1 bit/sample semantics
- exact Native DSD duration

FFmpeg remains useful for tags / cover metadata.

Supported local DSD extensions now include:

```text
.dsf
.dff
.dsdiff
```

Real `/media/extramusic` scan result after the fix:

- total library: **379 tracks**
- DSF: **11 tracks**
- real DSD256 metadata: `11,289,600 Hz / 1 bit / 2ch`

## Native DSD exact-tail rule

Another correctness issue was fixed:

DSF `sample_count` must describe an exact logical one-bit sequence. It must not be rounded up to a transport byte and accidentally treat padding bits as audio.

The implementation now requires alignment compatible with the Direct path (`sample_count % 32 == 0` in the tested representation) and rejects an intentionally malformed 31-bit fixture rather than padding/dropping bits.

This is covered by Native tests.

# 15. Recommended touch-reduction strategy

The next agent should continue the exact design direction already chosen.

## A. Renderer UI: restore upstream components, improve Web facade

Many current touches are merely:

```text
if (webRemote) hide Electron thing
```

That is the wrong long-term seam when the existing UI can keep its normal contract.

Prefer restoring upstream versions of:

- `src/components/layout/NavHeader.vue`
- `src/components/layout/SideBar.vue`
- `src/components/library/FolderManager.vue`
- `src/components/list/SongList.vue`
- `src/composables/useTrackMenu.ts`
- `src/composables/useWindowControls.ts`
- `src/layouts/MainLayout.vue`
- `src/pages/Library.vue`
- `src/stores/settings.ts`

and make Atom-owned `src/web/api.ts` implement the methods those components expect.

Examples:

### Window controls

Desktop:

```text
window.api.window.toggleFullscreen()
→ Electron
```

Web facade:

```text
same method
→ Browser Fullscreen API
```

Desktop-only minimize/hide/quit can be explicit unsupported/no-op facade behavior as appropriate, rather than requiring every upstream component to know about Web runtime.

### Settings / updater / lyric windows

The Web facade can satisfy subscription/query methods without actually creating desktop windows. Avoid lying about successful mutations that matter, but stable empty subscriptions / explicit unsupported responses are preferable to upstream UI surgery when the component only expects a capability surface.

### Local filesystem UI actions

For destructive/desktop-file actions (show in Explorer, edit tags, delete file), do not expose fake success.

If leaving original menus untouched makes dangerous actions callable remotely, either:

- make the Web facade explicitly reject them and ensure UI communicates failure, or
- justify the smallest single upstream seam for capability filtering.

Do not scatter many separate component changes.

## B. Queue: keep main authority but preserve upstream public signatures

Do **not** restore renderer queue ownership just to reduce touches.

Instead keep main authoritative session, but preserve the original public-facing renderer queue/player function signatures as much as possible.

This should allow restoring peripheral upstream callers such as:

- `src/composables/home/useDailyRecommend.ts`
- `src/composables/useQueuePanel.ts`
- `src/stores/streaming.ts`

The queue/core seam should internally forward mutation to main and apply the returned/session-event snapshot.

The architectural objective is:

```text
upstream callers keep normal API shape
        ↓
small modified queue/core seam
        ↓
main authoritative session
```

not:

```text
modify every upstream caller to know main session is async
```

## C. Headless server

Continue using Atom-owned:

```text
electron/main/atom/headless/routes.ts
```

The already-budgeted upstream:

```text
electron/main/server/index.ts
```

should remain only a thin mount/runtime-selection seam.

Do not put the Headless control plane back into upstream `server/routes.ts`.

## D. High-frequency Web sync

The upstream WS broadcaster intentionally suppresses `position` / `fftData`.

Instead of modifying it, the current direction is:

- low-frequency events via existing WS
- visible Web page polls `/status` at roughly 5 Hz
- hidden page is silent
- scan state can be polled while scanning

This follows the project’s “Hidden = silent” memory/traffic rule and removes the need to modify upstream WS internals.

## E. DSD scanner touch

`native/audio-engine/src/scanner.rs` is currently a new upstream touch beyond the original 31.

This one is a real functional gap: SPlayer’s local library does not discover Native DSD otherwise.

Do not blindly revert it unless the DSD scanning capability is moved to a cleaner already-touched seam without duplication.

Treat this as a potentially justified additional seam, but only after reducing all avoidable UI/store touches. If the final required count cannot remain 31, revisit the audit/budget only with an explicit architecture justification to the user; do not silently raise it.
