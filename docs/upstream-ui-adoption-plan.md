# Atom 上游界面吸收与小修方案

> 最后更新：2026-11-04

状态：**UI-1、UI-2 代码已实现，待浏览器/设备验收**；FIX-1、FIX-2 均已实现并通过隔离回归测试。
本文记录本轮讨论收敛后的范围、实施顺序和验收标准。代码存在不代表浏览器、账户或
输出硬件验收已经完成。

## 1. 目标与范围

本轮以 Web Control 的直接使用体验为主：新增 AM 风格播放页，让现有布局可以在播放页内
快捷切换，并提供紧凑歌曲列表。排序隔离随列表改造实施；扫描目录和下载扩展名分别作为独立小修。

| 项目               | 本轮安排                 | 交付结果                                               |
| ------------------ | ------------------------ | ------------------------------------------------------ |
| AM 风格播放页      | 第一批（已实现，待验收） | 封面下集中呈现歌曲信息和播放控制，另一侧显示歌词或队列 |
| 播放页布局快捷切换 | 第一批（已实现，待验收） | 在经典、全屏封面、AM 三种布局间切换，保留用户原有选择  |
| 紧凑歌曲列表       | 第二批（已实现，待验收） | 常规／紧凑两种密度，适配虚拟滚动和多碟分组             |
| 歌曲列表排序隔离   | 第二批（已实现，待验收） | 按页面类别保存偏好，不再跨页面串用                     |
| 扫描目录嵌套修复   | 独立小修（已实现）       | Core 写入前拒绝嵌套，取消 Web 写入后的撤销移除         |
| 下载扩展名修复     | 独立小修（已实现）       | 声明格式缺失时，补充使用响应文件名判断真实扩展名       |

界面批次优先交付，两个小修可分别提交，不作为界面改造的前置依赖。
本计划只定义这一轮工作的顺序；既有发布候选、输出和真实账户验收仍由
[路线图](./atom-roadmap.md)跟踪。

## 2. 明确排除与保留候选

以下项目已在本轮讨论中排除，不随上游代码引入：

- 酷狗分页与酷狗专属元数据补齐。
- 代理覆盖改造。
- 网络故障后的换曲策略调整；保留现有 Core 策略。
- 独立的全屏歌词布局、播放栏逐字高亮及相关模式设置。
- AutoMix、交叉淡化、对拍，以及 Electron／桌面窗口专属功能。

现有全屏播放器、歌词引擎、手机歌词展示和播放栏歌词继续复用。
封面共享过渡、布局快照动画和减弱动画设置留作后续体验打磨，本轮只使用必要的现有动画。

以下问题保留为后续候选，不与本轮界面改造捆绑：

| 候选                          | 已知事实                                         | 后续处理条件                                         |
| ----------------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| QQ 等实际使用平台的多碟元数据 | Atom 已有分碟 UI，部分平台字段映射不完整         | 用实际使用平台的多碟专辑确认字段后补齐映射           |
| 歌词正缓存刷新                | 普通歌词和 TTML 正缓存永久有效，已有手动清理入口 | 需要自动获取修订歌词时独立实施                       |
| 本地 TTML 多歌曲 ID           | 目前只索引首个 ID，仍有标题匹配路径              | 有相应歌词库使用需求时实施小补丁                     |
| ID3 前缀 MP4／M4A             | 生成样本在现有 native 产物中探测失败             | 收集实际文件后，独立验证扫描、解码和 seek 的容器适配 |
| TTML 官方 API 迁移            | 调查时旧镜像和官方 API 均可返回歌词              | 作为服务选择改进，不按当前已失效接口处理             |

## 3. 第一批：AM 播放页与布局切换

### 3.1 布局与交互

桌面 AM 布局采用上游的主要结构：封面下依次放歌曲信息、进度与时间、播放控制；
右侧显示歌词，打开队列时由队列占用该区域。隐藏歌词或当前曲目没有歌词时，
封面与控制区域居中。关闭队列后恢复先前的歌词显示选择。

复用 Atom 现有的播放、暂停、上一首、下一首、随机和循环操作，以及歌词定位、
收藏、歌单、下载和“所在文件夹”等适用入口。输出设备、音质信息和输出模式控件
仍通过现有组件或菜单可达；不复制上游的音量曲线与播放过渡控制。

播放器顶部增加一个布局选择入口，提供“经典”“全屏封面”“AM”三个选项，
外观设置页绑定同一份偏好。切换只改变呈现，播放位置、播放态、Core 队列和输出选择保持连续。
歌词／队列显隐继续复用现有 Web 展示状态，不为每种布局保存第二份播放状态。

响应式适配遵守现有 768 px／1280 px 断点：

- 桌面采用封面与歌词／队列双栏。
- 平板根据可用宽高收缩封面、间距和控制区，确保主要操作可见；空间不足时使用单栏。
- 手机采用封面与控制纵向排列，歌词、队列在同一内容区切换；沿用现有返回和收起交互。
- 无歌词、无封面、长标题及多艺术家时，信息与控制区仍可使用，不产生横向溢出。

### 3.2 状态与迁移

新布局偏好放在当前浏览器 settings 的 `player.layout`，可取
`classic`、`fullCover`、`apple`。这是现有 Web `player` 展示设置，
不加入 Core `SystemConfig.player` 或音乐域设置接口。

旧数据按以下规则一次性迁移：

| 旧偏好                            | 新偏好              |
| --------------------------------- | ------------------- |
| `coverLayout: default` 或没有旧值 | `layout: classic`   |
| `coverLayout: fullscreen`         | `layout: fullCover` |
| 已有有效 `layout`                 | 保留新值            |

迁移后移除旧 `coverLayout` 字段及其单独设置入口。新安装默认经典布局；AM 由用户选择。
已有封面比例、无歌词居中等参数继续保留，在适用的布局中展示对应设置。
布局、列表密度和排序均按浏览器持久化，不广播成其他 Control 的强制显示选择。

### 3.3 实现边界

主要入口为 `src/components/player/FullPlayer/index.vue`、
`src/settings/categories/appearance.ts`、`src/stores/settings.ts` 和 `src/types/settings.ts`。

对现有大组件做满足布局复用所需的有限拆分：

- 壳层统一管理展开／收起、页面可见性、时间订阅、背景以及沉浸模式生命周期。
- 共用封面、歌词区域及输出相关控件；歌词区域继续使用现有两套引擎及其设置。
- 经典、全屏封面和 AM 布局分别组织模板；复用现有命令客户端和 composable。
- 若共享参数需要跨层传递，只保留一个 Web 展示上下文，不引入新的播放服务或全局业务 store。

严格 Diretta 和 ALSA Direct 的处理锁定沿用现有规则。AM 中的音量入口必须复用或遵循
`useDirectModeState()` 与现有 Toolbar 的能力判断。Core/native 无需为布局切换新增合同。
浏览器隐藏、播放器收起或歌词区域不可见时，停止对应高频绘制；恢复时采用当前播放时间。

### 3.4 验收

- 三种布局可直接切换，刷新后保留选择；两类旧偏好均正确迁移。
- 连续播放中切换布局不重新加载音源，不改变位置、队列、随机／循环模式或输出。
- 歌词、队列显隐和手机返回路径正确；无歌词时布局完整。
- 播放、seek、收藏、所在文件夹和适用的下载／歌单操作仍可执行。
- Diretta／ALSA Direct 下音量与处理入口保持已有能力限制。
- 至少覆盖 1440×900 桌面、1024×768 平板和 390×844 手机视口，以及手机横屏。
- 记录三种布局及窄屏状态的浏览器截图，检查遮挡、长文本、点击目标和安全区。
- 隐藏／恢复页面后歌词时间正确，没有重复 RAF、时间订阅或后台持续绘制。

## 4. 第二批：紧凑列表与排序隔离

### 4.1 列表密度

在外观设置增加“常规／紧凑”选项，默认常规，复用本地 appearance 持久化。
只覆盖共用 `SongList` 的页面；Folder Browser 自己的列表／网格和 Core 显示排序保持原有合同。

紧凑模式收缩行高、封面、字号和项间距，桌面单曲行高度目标约 56 px；
常规模式沿用现有视觉。手机主要点击目标至少 44 px，必要时隐藏次要列。
单击播放、选择、批量操作和菜单行为沿用 Atom，不复制上游的双击播放或播放按钮行为设置。

`SongList` 的真实项高与 `SVirtualList` 参数一起更新。多碟标题继续使用现有可变高度路径，
不能把带分组的列表按普通固定行高计算。切换密度后重新测量可见范围，确保能够定位当前曲目。
只有实际验证发现共享虚拟列表缺少尺寸更新能力时，才补充该组件所需的最小修改。

### 4.2 排序偏好

将 `status.sortField/sortOrder` 替换为按固定页面类别读取的偏好，复用上游
`sortKey` 的思路。类别包括本地歌曲、喜欢的音乐、历史、艺术家、专辑和歌单等实际入口；
平台维度只在页面确有独立需求时使用有限枚举，不按专辑／歌单实体 ID 无限积累记录。

无排序作用域的临时列表使用组件内偏好。旧全局排序无法识别来自哪个页面，升级时清除旧字段，
各类别默认恢复 `none/asc`，不把旧值复制到所有页面。

显示排序与点击某行后的播放请求保持现有对应关系；不为隔离偏好重写 Core 队列策略。
专辑在默认排序下保留原始碟轨顺序和多碟分组。

### 4.3 验收

- 同一曲目数据在两种密度下无漏项、重叠或末尾空洞，播放和选择操作一致。
- 长列表滚动、定位当前曲目、触底加载和多碟分组正常。
- 更改歌曲页排序不会影响专辑、历史或喜欢页面；刷新后对应页面偏好恢复。
- 专辑初始打开使用默认碟轨顺序；切换密度不改变排序与当前播放。
- 为排序跨页面隔离编写行为回归测试；样式变化通过浏览器验证，不增加复述 CSS 的测试。

## 5. 两个独立小修

### 5.1 扫描目录嵌套

在 Core 现有添加和批量替换扫描根目录入口校验目录关系；添加入口在规范化后、写入前拒绝嵌套。
批量入口先完成整批校验再写入。使用 Linux 路径关系判断，兼顾重复目录、根目录和路径段边界。
复用已有目录规范化和查询能力，不建立第二套目录注册表。

Web 只消费成功结果或错误提示，移除添加成功后调用 `removeScanDir()` 的撤销逻辑。
已有扫描根目录不自动清理或删改。拒绝添加时，扫描根目录、曲目记录和本地歌单关联均不变。

回归覆盖父／子目录的两个添加方向、正常同级目录，以及投影过期的 Control；
用临时目录和隔离数据库断言拒绝后数据完整，不操作用户曲库。

### 5.2 下载扩展名

在现有 `downloadManager` 和 `filename` 工具中补充响应文件名解析。
优先级为：有效声明格式 → 响应文件名的已知音频扩展名 → MIME → URL 后缀 → 现有默认值。
仅使用响应文件名中的扩展名，保存目录和基本文件名仍由 Atom 下载命名规则决定。

覆盖有声明格式、标准 MIME、无后缀 URL 配合通用 MIME／响应文件名，以及无有效线索的情况。
重名、跳过、临时分片、标签和歌词旁文件继续走现有流程；不改变下载覆盖策略。
