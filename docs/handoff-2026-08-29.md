### Design

Do not introduce a second schema framework.

Current baselines:

```text

```

### Implemented behavior

`electron/main/database/migration.ts`

- exports explicit database schema version
- rejects unknown future `user_version`
- runs known migration steps inside a single SQLite transaction
- updates `user_version` inside that transaction
- if migration fails, schema changes and `user_version` roll back together

`electron/main/atom/runtime/configSchema.ts`

- defines the current durable settings schema baseline from the existing migrations list
- no second config migration framework

`electron/main/store/index.ts`

- rejects config files whose `__configVersion` is newer than this build supports
- continues to use existing upstream migration/deepMerge behavior for known versions

`electron/main/atom/runtime/dataMigration.ts`

- inspects existing durable DB/config before normal Core initialization
- rejects unknown future DB/config versions before modifying data
- only creates a backup if existing durable state actually needs migration
- does **not** create empty backups for fresh installs
- creates `data/backups/migration-*`
- database backup uses SQLite `VACUUM INTO`, not raw file copy, so WAL committed state is included consistently
- copies the durable `config/` directory as part of the migration snapshot
- therefore settings/provider credential/config files are included in the recovery snapshot

`electron/main/core-node/index.ts`

- runs migration preflight **before** loading store/database modules

`scripts/atom/stage-core-system.ts`

- `runtime.json` now includes database/config schema versions

`scripts/atom/check-core-artifact.ts`

- after final extracted Core starts and stops, verifies fresh durable data has:
  - `settings.json.__configVersion === 1`
  - SQLite `user_version === 4`

`electron/main/utils/paths.ts`

- only changed one internal import to an equivalent relative runtime-neutral import so the real migration helper can execute in ordinary Node tests
