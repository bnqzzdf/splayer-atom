# Atom 歌词改进方案

实施状态：P0/P1 已于 2026-09-18 完成，roadmap 中的验收项均有自动化回归覆盖。

## 1. 范围和结论

本方案只处理 SPlayer 最近歌词改动中对 Atom 有明确价值的 P0/P1 问题：歌词来源回退、候选竞争、无效歌词保护、TTML 首屏阻塞、插件抢占和逐词空格回归验证。

本轮不迁移解析器、不替换渲染器、不改变 Core/Web 协议形态，也不引入第二套歌词状态或缓存模型。

依据：

- Atom 当前已经有自己的 LRC、QRC、YRC、KRC、TTML、LyS、SRT 和 ASS 解析器。
- Core 已经负责平台歌词请求、匹配、歌词缓存、模糊匹配缓存和 TTML 缓存。
- Web 仍负责当前歌词的来源编排、解析后的展示投影和候选竞争；本方案只修复其中的实际错误。

## 2. 当前真实问题

### 2.1 显式平台偏好没有回退

`src/services/lyric/resolve.ts` 的 `resolveOnlineByPreference()` 在显式偏好下直接返回指定平台结果。设置文案表达的是“优先”，但无结果时不会继续尝试 `lyricSourceOrder` 中的其他平台。

目标行为：

1. 先请求指定平台；
2. 命中则立即返回；
3. 未命中则按 `lyricSourceOrder` 继续请求，但排除已经尝试的平台；
4. `self` 仍然只跟随歌曲自身来源，不做跨平台回退。

### 2.2 候选提交缺少统一有效性和质量门

`src/services/lyric/loader.ts` 当前存在多个直接提交入口。并发候选、插件结果、TTML 覆盖和预载结果没有完全共享同一套“解析有效 + 格式优先级 + 当前歌曲 token”判断。

这会导致：

- 低质量候选覆盖高质量歌词；
- 畸形歌词解析为空后清除当前有效歌词；
- 失败结果进入总流程清理逻辑；
- 旧歌曲或旧插件响应污染当前歌曲。

目标行为：所有候选先解析验证，再原子替换当前歌词。自动选择和后台升级只接受更优格式；用户显式切换平台时，允许按用户意图使用该平台的较低格式。

### 2.3 TTML 在部分路径阻塞首屏

普通在线平台路径会先提交基础歌词，但流媒体和歌词预载路径会等待 `resolveTTMLOverlay()` 完成后才产生最终结果。消费尚未完成的预载结果时，切歌后的歌词可能因此白屏。

目标行为：

- 流媒体和预载先展示基础歌词；
- TTML 在后台完成后再升级；
- 后台结果必须经过当前歌曲 token 和曲目身份校验；
- 下载歌词仍等待最终可用结果，不改为后台展示模型。

### 2.4 插件优选没有真正抢占

`withPluginPrefer()` 虽然提前发出插件请求，但会等待普通流程完成后才处理插件结果。插件较快返回时不能立即展示。

目标行为：插件返回即进入与内置平台相同的候选提交门；更优且有效时立即替换，较差或无效时忽略。

### 2.5 逐词空格需要验证，不预设迁移

SPlayer 的 `endsWithSpace` 是配合 `lyric-kit` 数据模型的改动。Atom 当前解析器在 YRC/QRC/KRC 中保留捕获文本，在 TTML 中显式保留 span 间的空格，因此不能直接认定 Atom 必然存在同一缺陷。

本轮只增加 YRC/QRC/KRC/TTML 英文逐词空格测试，并验证 TrackInfo、进度条歌词和复制歌词的输出。如果测试发现具体解析器丢失空格，再修复该解析器；不预先引入 `endsWithSpace`，避免形成两套空格表示。

## 3. 技术方案

### 3.1 统一候选提交

在 `src/services/lyric/loader.ts` 内部收口一个候选提交流程，复用现有 `useMediaStore().setLyric()` 和 `isBetterFormat()`，不新增歌词状态模型。

候选提交顺序：

1. 检查 token 和当前曲目身份；
2. 根据当前模式判断是否允许候选格式替换；
3. 在临时解析结果中确认存在有效歌词行；
4. 通过一次状态更新替换 `activeLyric`、原始内容和解析结果；
5. 解析失败或结果为空时保留旧歌词，不向 Core 推送空投影。

质量规则：

- 自动选择、插件竞争和 TTML 升级：候选格式必须高于当前格式；
- 首个有效候选且当前没有歌词：允许直接展示；
- 显式平台切换：该平台自身的有效候选优先服从用户选择，格式降级可以接受；其他回退来源仍必须通过格式质量门；
- 任何失败候选：不得清空当前有效歌词。

### 3.2 平台偏好回退

在 `resolveOnlineByPreference()` 中只修改显式平台分支：

- `self` 分支保持现状；
- 其他显式平台先查自身；
- 未命中后进入现有顺序查询逻辑，并过滤已尝试平台；
- 保留现有 `hasLocal`、`localFormat` 和 `smartPreferOnline` 约束。

不新增 resolver、adapter 或第二套平台注册表。

### 3.3 TTML 后台升级

将显示用加载路径中的 TTML 处理拆为：

- 基础歌词提交：不等待 TTML；
- 后台升级任务：请求 TTML，验证当前 token/曲目和解析结果后再提交；
- 升级失败：保持基础歌词。

流媒体和预载必须使用这一行为。下载歌词保留同步决议，因为下载结果需要确定最终导出内容。

Core 已有 TTML 请求去重和缓存，因此 Web 侧只需要避免阻塞显示，不新增网络缓存或去重层。

### 3.4 插件并发

插件请求仍由现有 `pluginClient.matchLyric()` 发起。只调整完成回调：

- 插件请求和普通来源并发；
- 任一候选返回后立即经过统一提交门；
- 普通来源为空时等待插件任务结束，再最终确认无歌词；
- 普通流程完成后不再额外重复提交同一插件结果；
- token 失效时丢弃迟到结果。

### 3.5 测试范围

新增或扩展：

- `src/services/lyric/loader.spec.ts`
- `src/services/lyric/resolve.spec.ts`
- `src/utils/lyric/parse.spec.ts` 或按格式新增最小测试

必须覆盖：

- 显式平台命中、未命中回退和 `self` 严格行为；
- 高格式先到、低格式后到时不降级；
- 低格式先到、高格式后到时升级；
- 畸形 TTML 保留基础歌词；
- 流媒体和预载不等待 TTML 首次展示；
- 插件较快返回时立即抢占；
- 快速切歌时旧请求不污染新歌；
- YRC/QRC/KRC/TTML 英文逐词空格输出。

## 4. 验收标准

- 指定平台无歌词时，其他已配置平台可以继续匹配。
- 有效高质量歌词不会被低质量候选覆盖。
- 任意畸形或空解析结果不会清空已有有效歌词。
- 流媒体和预载不会因 TTML 网络请求导致歌词首屏白屏。
- 插件歌词可以在更快返回时立即参与竞争。
- 快速切歌、刷新偏好和预载消费不会出现旧歌词污染。
- 英文逐词歌词在歌词页、TrackInfo、进度条和复制结果中通过空格回归测试。
- 不引入 `lyric-kit`、`lyric-dom`、新的歌词协议、第二套缓存或第二个歌词权威。

## 5. 明确不做

本轮不做：

- 全量替换 Atom 现有歌词解析器；
- 引入 `lyric-kit` 并改写共享歌词类型；
- 用 `lyric-dom` 替换现有歌词渲染器；
- 引入 `endsWithSpace` 作为第二套空格表示；
- 桌面歌词、任务栏歌词、动态岛等 SPlayer 专属功能；
- Core 全面接管歌词解析和 canonical lyric 状态；
- 将下载歌词改成后台异步决议。

Core 权威化属于后续独立架构工作，不纳入本轮 P0/P1 歌词改进。
