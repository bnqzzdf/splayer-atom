# SPlayer Atom — Findings & Decisions

## 2026-08-29 — P1 Core-owned playback implementation closure

- Core-owned playback is now implementation-complete at the architecture level: canonical Track resolution, playback policy, bounded failure recovery, song-cache scheduling, next-track preload, Diretta staged-next/boundary, reload-current, output switching, native lifecycle and Desktop/Web command transport all converge on the same `PlaybackSession`.
- Desktop renderer no longer owns a raw playable-source load path. Remaining renderer `audioSource` logic is compatibility/non-authoritative code; playback commands and natural lifecycle do not depend on it.
- Private FM recommendation ownership moved into Core and projects its canonical queue/mode through the same session contract. Auto-close and Fuck DJ policy also moved into Core so Control disconnect cannot silently disable playback policy.
- Upstream plugin playback compatibility exposed a hidden Node-Core blocker: the existing plugin registry/router depended on Electron `app` / `utilityProcess` / `net`. The sandbox itself is Node `vm`, so no new plugin framework was created. Three narrow upstream files were made runtime-neutral; Desktop injects `utilityProcess`, Node Core uses `child_process.fork`, and both reuse the existing host.worker/router/registry.
- Node Core now builds `index.js` plus `plugin-host.js`; an ordinary Node fork receives `hostReady` and answers ping/pong. Production Core JS remains free of Electron runtime imports. Runtime-neutral seam budget is therefore explicitly 16 while business budget remains 37 and Core-authority seam budget remains 12.
- Core resolver now preserves inherited upstream plugin semantics without expanding Atom provider scope: Netease is official first → plugin fallback → allowed trial; QQ Music/Kugou only use inherited `musicUrl` plugin compatibility; Qobuz/TIDAL remain Atom official-provider paths.
- Full automated gate after this closure is Node 134/134 and Web 52/52, with Node/Web typecheck, ESLint, Prettier, Core build, zero-Electron audit, plugin-host smoke, touch audit and `git diff --check` passing.
- Roadmap section 5 implementation boxes can be marked complete, but real acceptance remains separate: Netease three-track/no-Control continuity, live URL-expiry recovery, real ALSA/Diretta combinations, and Qobuz/TIDAL account-backed playback are not implied by static/automated architecture proof.

## 2026-08-27 — Local safety commits and recovery-path inspection

- 用户新增的 proven oracles 路径已确认：`tinyLMS`、`tinylms-next`、`slim2Diretta`、`DirettaRendererUPnP`。四者仅作为连接/生命周期行为证据；Atom 仍不得复制它们的播放器、重采样、全轨 RAM、重试或 watchdog 架构。
- `DirettaRendererUPnP` v2.5.10 README 记录了一个与 Atom 现象高度一致的已修缺陷：Target 超过约 2 秒才进入 online 时，发送侧因 ring 为空而停止接收/填充真实音频，Target 持续收到静音并无法完成 online，形成死锁；其修复允许 `sendAudio()` 在 online 超时后继续填 ring，使 Target 收到真实数据并正常转为 online。Atom 当前 paused-load 顺序同样是“等待 online 后 `load(false)` 才返回，而 `play()` 只能随后调用”，需检查是否存在相同的上线前真实数据/启动握手闭环。
- 新一轮离线对照必须区分 SDK 149 `SinHost` 中的两种调用模型：`SyncBuffer` 示例使用 `setSink(..., false, mtu)`，而直接派生 `Sync` 的示例使用 `setSink(..., true, mtu)`。Atom 的 `DirectSync` 直接派生 `DIRETTA::Sync`，因此不能仅因 tinyLMS 使用 `false` 就认定该布尔值错误；需先核对 tinyLMS 的具体基类、数据供给模型和完整时序。
- 完整源码确认 tinyLMS 的 `DirettaSyncImpl` 同样直接派生 `DIRETTA::Sync`，并在用户已验证的长期播放路径中使用 `THRED_MODE(289)`、按 MTU/源码率计算的 info cycle、`setSink(..., 30 ms, false, measured_mtu)`、优先 PCM32、相同的 `MSMODE_AUTO`、`connectPrepare(true)`、`connect(0)` 和 `connectWait()`。因此它与 Atom 属于同一 pull-callback 调用模型，不是 `SyncBuffer` 架构差异。
- SDK 头文件把 `setSink` 第三个参数描述为“Disable Sink's playback rejection (NOP)”。官方直接派生 `Sync` 示例传 `true`，tinyLMS 则传 `false`；结合头文件与后续实测，这个差异不是连接修复变量，Atom 保持官方 pull 示例的 `true`。
- 对 44.1 kHz / 16-bit / stereo 静音输入，Atom 与已验证 tinyLMS 的连接前差异矩阵为：线程模式 `5` vs `289`；info cycle `100 ms` vs 约 `8231 us`；Sink buffer `100 ms` vs `30 ms`；NOP `true` vs `false`；wire PCM `S16` vs 优先 `S32`；transfer 最长恢复周期 `100 ms` vs `30 ms`。连接顺序和 Target/interface/MTU/`MSMODE_AUTO` 相同。成功后的 300 ms 等待不可能解释进入 online 前的超时。
- Git 历史确认 Atom 第一次真实 Direct paused load 成功时的 bridge 已使用当前相同的 mode 5 / 100 ms / NOP `true` / exact S16 / 100 ms transfer 参数；之后 `55fa9eb` 才把 `connectWait()` 替换为固定 10 秒 `is_online()` 轮询并加入清理。故这些基础参数至少曾完成过同一 DX5 II 的连接，当前首要回归差异是过早的 10 秒截止，而不是应先复制 tinyLMS 的调优/位宽策略。
- SDK 自身 `connectWait()` 的观察窗口约 50 秒，而有效 root 测试在约 10.76 秒由 Atom 自己返回超时。现有静态事实只能证明 `is_online()` 可观察最终状态，不能证明 10 秒足以覆盖正常 Target 协商；因此 `55fa9eb` 的 10 秒常量可能把仍在 SDK 合法连接窗口内的请求误判失败。下一证据应来自 tinyLMS 已有连接日志或一次经用户确认的延长窗口单变量测试。
- 本机 systemd journal、当前进程和用户目录未找到这次手动 tinyLMS 长播放的结构化连接日志，无法离线量出其 `connectWait()` 耗时。不能把“可能超过 10 秒”升级为已证实；修复必须仍保留明确上限，并通过下一次用户确认的单变量实测闭环。
- 当前 Rust 静态回归只断言 bridge 存在 `kConnectTimeout`、轮询 `is_online()` 且不调用 `connectWait()`，没有约束等待窗口的最小量级，所以 10 秒误截断不会被自动测试发现。最小候选修复是仅把有界窗口扩展到 60 秒并锁定该常量；继续保留 2 秒有界清理与原有协商/格式/RT callback，不同时改任何 tinyLMS 调优参数。

## 2026-08-26 — Diretta Source Direct correction

- Product requirement supersedes the earlier "reuse current SPlayer DSP output" assumption: Diretta is a strict Source Direct path, not merely a network output backend. SPlayer UI/media/queue/source-resolution/player state remain upstream-owned, but the normal audio-processing path may be bypassed where it alters source audio.
- Current SPlayer normal playback always constructs a player `Resampler` targeting `f32`; every decoded frame is passed through `player_resampler.process::<f32>()` before output, then may pass normalization, EQ, tempo/pitch and software volume/fade. This is incompatible with an unambiguous bit-transparent integer PCM path, especially for 32-bit integer PCM because `f32` cannot represent all 32-bit integer sample values exactly.
- The `ffmpeg_audio` dependency already exposes `AudioFrame::raw_data<T>()` as a safe zero-copy view over the decoder's `AVFrame` for `i16`, `i32`, `u8`, and `f32`, including packed and planar layouts. A Diretta direct path can therefore branch immediately after decode instead of writing another decoder.
- `ffmpeg_audio` documents the exact valid-bit semantics: 24-bit content may decode as `S32` with 24 valid bits and zero padding. Source Direct may use a wider integer transport slot only when those effective source bits are preserved unchanged; this is representation padding, not DSP or quantization.
- The old `/home/bnqzzdf/code/tinyLMS` is not a full Source Direct reference for PCM: its generic FFmpeg path explicitly normalizes output to `AV_SAMPLE_FMT_S32`, invokes Swr/SoXR, can downsample above target capability, and can upsample low standard-divisor rates to 48 kHz. Its Diretta callback zero-copy ideas are useful, but its PCM transformation policy must not be copied.
- Strict Diretta PCM invariants are: original sample rate; original channel count/layout; unchanged effective integer sample bits or unchanged decoded float representation when exact float transport is supported; no resample/remix/EQ/normalization/software volume/fade/tempo/pitch/re-encode; no silent compatibility fallback if the Target cannot accept the exact representation.
- Native DSD is a separate direct bitstream problem. Current SPlayer has no DSD-specific path, so DSD must not enter the normal FFmpeg-to-PCM player pipeline. DSF/DFF/native DSD payload extraction and Diretta native DSD negotiation must preserve source bits and bit order except for explicitly proven lossless wire-layout adaptation required by the Target.
- For compressed lossless sources such as FLAC/ALAC, lossless decode to the exact original PCM samples is decoding, not transcoding. For lossy codecs, bit-perfect equivalence to the compressed bitstream is not meaningful; Source Direct should mean no sample-rate/channel/DSP processing after the codec's native decode output, with exact Target representation negotiation and truthful UI status.
- Zero-copy must be defined by ownership, not slogans. The desirable PCM case is an FFmpeg-decoded frame or ref-counted frame buffer whose sample payload remains stable while Diretta `getNewStream` borrows it; the SDK callback must not allocate/copy/lock. If the decoder emits planar data but the Target requires packed interleaving, that layout transform is a real copy and must be treated explicitly rather than hidden under a zero-copy claim.
- The current public `AudioFrame::raw_data` borrows the internal frame only until the reader advances. An asynchronous Diretta callback therefore needs a minimal retained-frame ownership seam (for example an `AVFrame` ref/clone that increments FFmpeg buffer references without copying sample payloads) before true zero-copy can be proven. Do not use unsafe lifetime extension or advance/reuse a streaming ring region while the SDK may still hold its pointer.

## 2026-08-26 — APE + Native DSD HiFi Gate findings

- FFmpeg's APE decoder advertises only planar PCM outputs (`u8p`, `s16p`, `s32p`). This is the same memory-layout issue already solved for ALAC/WavPack, not a fidelity limitation. APE16 therefore reuses the exact integer planar→interleaved repack and is proven with a real 104-byte Monkey's Audio fixture.
- The local FFmpeg build has no APE encoder, so no locally generated APE24/32 codec-specific fixture is available. The production implementation does not branch on codec: APE `S32P` is consumed by the same full-range S32P repack already mechanically proven with WavPack32. Keep this distinction explicit until a real APE24/32 fixture is available.
- APE `u8p` is intentionally outside the current strict Direct set. Diretta exposes signed PCM8, and unsigned→signed conversion is reversible but changes the sample bit representation; do not silently classify it as bit-identical Source Direct without a separately approved representation rule.
- Native DSD must bypass FFmpeg completely. The new direct DSD path parses DSF/DFF containers itself, streams fixed-size blocks, and never creates PCM, float samples, a resampler, DoP, gain, or DSP state.
- DSF's source representation is LSB-first and block-planar by channel; DFF raw DSD is MSB-first and byte-interleaved. Diretta `FMT_DSD_SIZ_32` requires a 4-byte-per-channel L4R4 wire layout, so both containers require a lossless memory-layout repack even though every original DSD bit remains unchanged.
- Unlike old tinyLMS, Atom does not pre-reverse DSF bits to MSB and does not try opposite-order/forced-LSB fallback. SDK 149 explicitly supports both `FMT_DSD_LSB` and `FMT_DSD_MSB`, so Atom requests the exact source bit order plus `FMT_DSD_BIG`; an incompatible Target fails strictly.
- A standalone SDK 149 format probe confirms DSD64 LSB+BIG+SIZ32 and MSB+BIG+SIZ32 are both valid `FormatConfigure` values with `isDSD=true`, `getBits=1`, `getSpeed=2822400`, and 2 channels.
- The new native DSD ring uses eight preallocated output slots with the same FREE→FILLING→READY→IN_FLIGHT→FREE ownership protocol as Direct PCM. The Diretta RT callback only borrows the stable repacked pointer; it never performs the DSF/DFF transform itself.
- Synthetic DSF/DFF fixtures prove exact native-bit preservation and L4R4 ordering, callback pointer identity, strict underrun, and rejection of an unrepresentable DSD_SIZ_32 tail. Real TagLib 10 ms DSF and DFF fixtures also fully drain through the parser as exactly 7056 bytes each.
- The common C++ connection lifecycle was extracted only after PCM and DSD became two concrete callers. Format construction remains separate and concrete; this is reuse of repeated SDK connection plumbing, not a new output/backend framework.

## 2026-08-26 — PCM Source Direct HiFi Gate implementation

- A separate Atom-owned `direct_pcm` core now uses the already-linked FFmpeg C API directly for demux/decode into fixed ref-counted `AVFrame` slots. It does not create the SPlayer player resampler and does not enter normalization/EQ/tempo/software-volume/fade processing.
- Packed integer output (`S16`/`S32`, including 24 valid bits in S32) is true zero-copy after codec decode: the pointer returned to the Diretta SDK callback is exactly the FFmpeg `AVFrame.data[0]` payload pointer, and the slot stays `IN_FLIGHT` until the next callback releases it.
- Current bundled FFmpeg outputs ALAC and WavPack as planar integer PCM (`S16P`/`S32P`). This is not an audio-fidelity limitation: the samples are exact PCM values. Atom now performs one integer-only planar-to-interleaved repack in the non-RT decode producer, then the Diretta SDK borrows that stable packed buffer without further copy.
- The planar repack changes only memory layout. It performs no float conversion, resampling, quantization, channel mixing, gain, or re-encoding. ALAC/WavPack therefore remain Source Direct and bit-perfect even though their memory path is `BitPerfectRepack` rather than `ZeroCopyPacked`.
- Fixture tests mechanically prove ALAC16/WavPack16 sample identity, ALAC24/WavPack24 valid-bit identity, and WavPack32 full 32-bit identity after repack. WAV16/24/32 and FLAC24 packed paths remain bit-exact; float PCM is explicitly rejected by the strict direct core.
- Planar repack buffers are reused per fixed ring slot. ALAC exposes a frame-size hint; WavPack may report `frame_size=0`, so the producer may grow a slot only when a larger variable block is actually decoded. Allocation never occurs in the Diretta SDK real-time callback.
- The production Diretta bridge now derives from `DIRETTA::Sync` and implements pull-mode `getNewStream()`. The callback only releases the prior block, requests the next stable pointer/size from Rust, and assigns `stream.Data.P/Size`; regression tests forbid `memcpy`, `setStream`, `resize`, mutexes, discovery, or format setup inside that callback.
- Exact PCM negotiation currently supports S16 and S32 transport at the original source sample rate and channel count. Unsupported Target combinations fail explicitly; no 32→24/16 fallback, resampling, remix, or silent processed path exists.
- DirettaHostSDK 149 Linux x64 static archives are non-PIC, so a normal Rust `cdylib` link initially failed even though executable/test links succeeded. A standalone link probe showed the safe in-process solution: statically bind libstdc++ and link the final addon with `-Bsymbolic`. The real release `audio-engine.node` now links and loads successfully with no `TEXTREL` and no dynamic `libstdc++.so` dependency, preserving the single-address-space zero-copy design.
- Premature NAPI/TypeScript Diretta device-scanning exposure was removed from this HiFi Gate. Until the user approves the audio proof, the Diretta direct core remains an internal optional native seam compiled only for `atom_diretta`/tests; ordinary no-SDK SPlayer builds contain no Diretta direct core and remain warning-free.
### 2026-08-27：四组可工作实现的连接完成语义

- `tinyLMS`、`slim2Diretta`、`DirettaRendererUPnP` 的源码连接路径，以及 Diretta SDK 自带示例，都在 `connectPrepare()` / `connect(0)` 之后调用 `connectWait()`。
