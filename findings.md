# SPlayer Atom — Current Findings & Decisions

## Current Findings

- Existing Core Control Protocol routes are sufficient for hardware release diagnostics: `/api/info`, `/api/status`, `/api/session`, and `/api/output/devices` provide release identity, player/session state, and ALSA/Diretta discovery without adding a high-authority debug API. Output selection and queue-index playback already have explicit Core commands, so the diagnostic stays read-only unless the operator supplies a state-changing flag.
- A safe session report must project canonical Track metadata rather than serialize the snapshot. The acceptance diagnostic keeps id/source/title/artist/album/duration/quality, while excluding local/CUE paths, cover URLs, final playable URLs, provider credentials, cookies, and Authorization. It also refuses a PCM/Native-DSD checkpoint when queue quality metadata cannot prove the requested class.
- Automated observation can prove only Core session transitions. DAC sample-rate/DSD indication, true bitstream preservation, audible continuity, Diretta Target availability, and hardware privilege behavior remain manual evidence in `docs/hardware-release-checklist.md`; real provider entitlement/data paths remain credential-dependent evidence in `docs/live-provider-acceptance.md`.
- Formal product identity is now **SPlayer Atom** with an independent `0.1.0` version line. Runtime/release identity is separated from upstream provenance: package/repository/appId/updater/publish/artifact names point to `bnqzzdf/splayer-atom`, while `scripts/atom/upstream.json` remains the explicit SPlayer source baseline. A dedicated 14-file product/release-identity seam covers packaging/updater plus unavoidable user/third-party identification surfaces (Desktop lyric title, Jellyfin/Subsonic client IDs, Atom contributors) without silently raising the 105 business-touch budget.
- Release provenance must distinguish a Git commit from an exact dirty worktree. Core `runtime.json` and `/api/info` therefore expose Atom version, commit, `sourceDirty`, accepted SPlayer baseline, protocol/runtime/capabilities; Desktop packaging injects the same commit/dirty/baseline into packaged metadata. Local uncommitted artifacts correctly report `sourceDirty: true`, while formal clean CI is expected to report false.
- `orpheus://` is a compatibility identifier rather than ordinary branding. Atom therefore keeps the upstream scheme parser/runtime registration, but removes all installer-level static protocol claims. The feature remains default-off and only calls `setAsDefaultProtocolClient("orpheus")` after explicit user opt-in, so installing Atom does not silently steal SPlayer-Next's scheme while existing web-open links remain usable when requested.
- Release identity now has artifact-level evidence beyond static config: Desktop unpacked packaging succeeds with executable `splayer-atom`; packaged asar reports `splayer-atom` / `SPlayer Atom` / `0.1.0`, Atom commit + dirty state + SPlayer baseline + Atom repo/bugs URL; a real Linux AppImage is named `splayer-atom-0.1.0-x86_64.AppImage` and its `latest-linux.yml` references only that Atom asset. Formal release workflow also rejects non-`bnqzzdf/splayer-atom` repository context and dirty source trees.
- About/diagnostics consumes shared `getCoreInfo()` instead of relying only on renderer build constants, so Desktop/Web can directly report Core version, Atom commit, SPlayer baseline, Core Protocol, source dirty state and Core Node runtime. Protocol compatibility remains explicitly independent of product version; tests accept widely different product versions when protocol v1 matches.

- Deterministic playback acceptance can drive the real `playbackSession` without production-only injection seams by launching an isolated Node 24 test process with experimental module mocks and the existing `tsconfig.node.json` aliases. The harness replaces native player/provider/storage edges but executes the real authoritative session state machine.
- The new behavior harness proves three online canonical Tracks with playlist `PlaybackContext` advance 1 → 2 → 3 solely from `onNativeEnded()`, with no renderer/Control callback; it also proves one same-track fresh resolve is allowed, a second `sourceError` advances immediately, and a failed fresh resolve advances to the next queue item. The same harness now covers fake ALSA → Diretta output switching: the current HTTP source is materialized/reloaded for Diretta and the following track still advances through the same Core session. This closes the software-verifiable Roadmap auto-next/continuous-play/expired-URL/output-switch acceptance without credentials or hardware.
- Netease `fee=4` was a genuine classification bug in the authoritative Core resolver: `fee=1` and `fee=4` both became `NETEASE_VIP_REQUIRED`. A new `NETEASE_PURCHASE_REQUIRED` code now distinguishes digital purchase from membership entitlement, remains a track-scoped skippable Core error, and has separate zh-CN/en-US copy. To keep the upstream business-touch budget at 105, Atom-specific ProviderAccounts/Web service filtering moved into the already-touched schema aggregation seam and `src/settings/categories/services.ts` was restored exactly to upstream before adding `shared/types/errors.ts`.
- P4 `/config` audit found no active HTTP consumer: Web This-Control uses its local allowlist, shared Core Settings uses `/settings/core`, Desktop uses local Electron config IPC, and the retained legacy inventory asks for narrowly allowlisted `/settings` rather than `/config`. Removing the two generic Core/Headless routes therefore reduces authority surface without compatibility substitution or a new API.
- The optional bundled Node artifact can stay a packaging-only variant because the existing launcher already prioritizes `runtime/bin/node`. `--bundle-node` now stages the build process's reference Node executable only after the existing exact `24.18.0` guard, records `nodeBundled` in `runtime.json`, and uses the same app/native/data/protocol payload as system-runtime. The final artifact gate launches with no `ATOM_NODE_BIN` override and checks `/proc/<pid>/exe` against the staged Node, so a hidden fallback to system Node cannot pass. The runtime also carries the reference Node distribution `LICENSE` and the artifact gate requires it.
- Music download has a single product destination: the Core host. Making `DownloadRequest.destination` a fixed `"core"` literal is preferable to introducing a destination enum because Control-local music download is explicitly out of scope, not a future branch of the same queue. This keeps queue/dedupe/path/tagging authority in one Core domain while UI copy makes the remote filesystem boundary explicit.
- Normal browser runtime already mounts the shared SPlayer `App`/router through `mountSPlayer(true)`; the separate `HeadlessApp` is only a `/debug` diagnostic page. Combined with existing Library/session clients, this means local browse/search/playback is a shared-Control software path rather than a second Web product. Netease Favorites/Daily/Cloud also reuse the same `useUserStore`/provider-session state and `providerClient`; only local Cloud upload remains a Host capability. Real account content behavior still requires live acceptance and should not be inferred from static reachability.

- The Netease API replacement assessment starts against a dirty worktree containing unrelated Settings convergence changes. Product source will remain untouched; only the existing planning records will be updated for this research task.
- Architecture constraints make this an adapter/runtime-seam question: Node Core must remain the provider/session authority, Netease compatibility must remain active, and the migration should not create a second provider model or route family.
- The repository vendors its Netease implementation under `electron/main/apis/netease/`: one `callNetease(name, params)` entrypoint, roughly 70 route modules, and shared cookie/request/crypto/device/NCM-BL internals. There is no package-manager dependency on the Node `NeteaseCloudMusicApi` project to swap mechanically.
- Core-side consumers are already concentrated on `callNetease`: provider Control routes, playback source resolution, lyrics, comments, recognition, cloud upload, Personal FM, scrobbling, and MCP online search. Renderer feature adapters call the same provider contract through `window.api.apis`; the best migration seam is therefore below `callNetease`, provided response bodies and cookie semantics can be preserved.
- Roadmap §7 treats Netease as an actively maintained reference provider. A replacement must retain Web search, real session use, VIP/SVIP full URLs, Diretta playback, favorites/account reads, and must not regress the remaining acceptance work (Core-owned auto-next, continuous playlists, Headless pages, URL refresh, and `fee=4` distinction).
- The local Netease subsystem is about 4,000 lines including focused tests. `index.ts` owns durable SQLite-backed cookies, anonymous `MUSIC_A` bootstrap, device identity, session mutation, a two-minute response cache, optional CN IP injection, and named-module dispatch; `request.ts` owns proxy-aware HTTP, request/response normalization, and `weapi`/`linuxapi`/`eapi`/`api`/`xeapi` crypto modes.
- The public compatibility contract is narrow but behavior-rich: callers expect `Promise<{status, body}>`, `NeteaseRequestError` to retain status/body, arbitrary named calls via the Control protocol, and Core-readable `MUSIC_U` session state. This favors replacing internals behind the existing TypeScript facade instead of changing renderer/Core call sites.
- Direct Core callers use a smaller critical subset (`song_url`, `song_download_url`, `cloudsearch`, `lyric_new`, Personal FM, audio match, cloud-upload calls, and scrobble), while renderer-facing product pages exercise a much broader module set dynamically. Playback-only parity is therefore much smaller than full product parity.
- The browser/search backend returned no rendered content for the supplied GitHub repository. External-source inspection will use a read-only temporary Git clone and stable GitHub file links for attribution.
- The supplied repository currently points its Cargo metadata and README links at `SPlayer-Dev/ncm-api-rs`; inspected commit `133b65bfe482e41ebccf018870d3fce07bf58eb3` (2026-04-07). It is a single Rust crate, version `0.1.0`, with optional `server` feature and an Axum `ncm-server` binary.
- `ncm-api-rs` offers two integration shapes: direct Rust library calls through `NcmClient`, or a standalone HTTP server. The latter is the only straightforward fit for the current Node Core unless Atom adds a native addon/FFI bridge.
- Feature coverage is broad (hundreds of route modules) and includes most named surfaces visible locally: search, song URLs/download URLs, detail/lyrics, playlist/album/artist/user/account, QR/login, FM, recommendations, comments, cloud, audio match, scrobble, and proxy/real-IP support. The README claims Node-compatible REST routes, but this must be validated against actual router/path/response/cookie behavior rather than accepted as sufficient evidence.
- The Rust crate currently implements `weapi`, `eapi`, and `linuxapi`; the existing Atom implementation additionally has `api`, `xeapi`, device/anonymous-session and NCM-BL-specific logic. Coverage by route name alone does not prove behavioral parity for Atom's enhanced paths.
- The HTTP server is stateless with respect to Atom's durable provider session: it constructs one shared `ApiClient` whose initial cookie is fixed, accepts a per-request cookie, and forwards provider `Set-Cookie` headers. An Atom adapter would still need to load/persist/merge cookies and stable device identity in Node Core; delegating session authority to the sidecar would violate the current architecture and lose current behavior.
- HTTP request parameters are flattened to strings by the Axum server. That is broadly compatible with the original Node API style, but Atom must provide a serialization adapter for nested/array values and test each mutating route; raw TypeScript object parity is not automatic.
- Critical same-name methods are not necessarily equivalent. Rust `song_url` uses the older `/api/song/enhance/player/url` + `br`, while Atom's `song_url` deliberately uses `/v1` + `level` and `xeapi`; Rust has a separate `song_url_v1` method that is a better target. The same issue exists for download URL (`song_download_url` versus `song_download_url_v1`).
- Other concrete behavioral gaps found in source: Rust anonymous registration uses `weapi` rather than Atom's current `xeapi`; Rust scrobble sends one older/weapi payload while Atom's current legacy mode uses two eapi client-log calls and supports richer source metadata. These are acceptance-sensitive customizations, not facade-only differences.
- Filename comparison shows Rust has about 380 API modules versus roughly 70 registered Atom modules. Eleven Atom module names lack an exact Rust filename: six custom cloud-upload stages, `like_v1`, `playmode_intelligence`, `scrobble_v1`, `song_simi_get`, and `song_wiki_info`. Most have conceptually related Rust methods under different names, so each needs an explicit compatibility mapping and response/parameter test rather than a simple name transform.
- Product-page usage confirms full replacement scope is substantial: login/QR/refresh/logout; cloud list/delete/upload; playlists CRUD/order/tracks/subscription; albums/artists and subscriptions; daily recommendations, Heart Mode, FM; favorites/like; search; comments; lyrics; audio recognition; source/download URL resolution; and scrobbling.
- Several call contracts require adapter care: cloud delete passes an array, playlist reordering passes pre-serialized JSON, QR login expects `cookie` in the response body, login refresh expects a body cookie string, and the current Core independently persists response `Set-Cookie`. Route coverage must include these exact shapes.
- Atom's release architecture makes a sidecar a product-level change, not a dependency swap. Both Electron packages and the formal Linux x64 Core tarball would need to build/stage the Rust binary, locate it at runtime, supervise startup/readiness/shutdown/crash recovery, propagate proxy/session settings, and extend final-artifact smoke checks and runtime provenance.
- Directly linking the Rust crate would require a new N-API/FFI addon or folding provider code into the audio-engine addon. The latter violates responsibility boundaries; a dedicated addon avoids a process but increases cross-platform native build/ABI/type/bundling work. A private loopback or stdio sidecar is the smaller architectural delta.
- Rust source tests are much narrower than Atom's acceptance surface: public live integration tests cover only banner/search/song detail/toplist/hot search/login-status/country codes; unit tests cover Query/error helpers. There are no authenticated, VIP URL/download, QR-cookie persistence, cloud upload, scrobble, proxy, server-route parity, or long-lived-session tests.
- The server's compile-time route generator explicitly excludes the multi-method cloud modules (`cloud`, `cloud_upload_token`, `cloud_upload_complete`), and the visible router manually adds only avatar/voice upload routes. Therefore several cloud methods offered by the library are not exposed by the current HTTP server; the HTTP mode cannot cover Atom cloud upload as-is.
- `cargo test --no-run --features server` passes at inspected commit `133b65b`, including compilation of the library, Axum server, and test targets. This establishes buildability on the current Linux toolchain, not runtime/provider parity.
- Rust and Atom request layers share the same general body-code-to-status normalization and special success codes, so error adaptation is tractable. One known response-shape difference is `login_status` (Rust returns the provider body directly; Atom wraps successful data), but current renderer code already tolerates either shape.
- A release `ncm-server` build with the `server` feature succeeds on Linux. Native compilation is therefore not the principal feasibility risk; behavior parity, lifecycle integration, and multi-platform artifact production dominate.
- The locally built unstripped Linux x64 server is 19 MiB, links only standard glibc/libm/libgcc runtime libraries, starts successfully on loopback, uses about 9.1 MiB RSS at idle, and returned a valid public `cloudsearch` response. The README's low-memory direction is plausible, though final stripped/package size and sustained-load memory still need measurement in Atom's artifact gate.
- Repository maturity is modest: the canonical `SPlayer-Dev/ncm-api-rs` has one `v0.1.0` release (2026-04-07), 55 stars/11 forks/2 open issues at inspection time, and no commits after 2026-04-07. Prebuilt assets cover Linux x64/arm64, macOS x64/arm64, and Windows x64. This is usable as a base, but Atom should pin a commit and expect to own compatibility patches rather than rely on rapid upstream response.
- The user-supplied `bnqzzdf/ncm-api-rs` repository appears to be a newly created mirror/transfer surface whose code metadata points back to `SPlayer-Dev/ncm-api-rs`; the canonical source/release history is currently under the organization repository.
- Batch comparison of common module names found widespread endpoint/crypto differences beyond the previously identified URL methods. Some are harmless representation differences (Rust default means eapi; template URLs evade simple extraction), but others are real: Rust `like` targets the older radio-like endpoint while Atom `like` targets song-like, and several Rust methods choose weapi where Atom deliberately uses current eapi/xeapi paths.
- Rust does contain conceptually related replacements (`song_like`, `simi_song`, split cloud methods), but using them requires an explicit Atom name→Rust method compatibility table. Generic underscore-to-slash routing cannot preserve current behavior.
- Additional high-risk deltas: Atom `like_v1` uses xeapi `/api/v1/radio/like` and falls back to weapi `/api/song/like`; Rust exposes older `like` and a separate `song_like`, with no xeapi. Atom `audio_match` validates inputs, uses a random session ID, Core proxy, headers and an 8s timeout; Rust hardcodes a session ID, creates a fresh direct client, and bypasses its normal proxy/timeout path.
- Atom's `scrobble_v1` is a full NCM-BL PLV/PLD implementation with current metadata/source handling; no equivalent exists in the Rust crate. A full replacement must port about 500 lines of NCM-BL/play-log logic or intentionally drop the current default scrobble mode, which would be a product regression.
- The Rust issue tracker confirms a product-relevant known incompatibility: open issue #2 reports `playlist_tracks` fails because the Rust method uses eapi while the Node reference uses weapi. Atom actively supports playlist add/remove, so the current release cannot be adopted unchanged even before Atom-specific deltas are considered.
- The only current release/CI run is from 2026-04-07; two compatibility issues opened in July remain unresolved as of inspection. This supports treating a maintained Atom fork/pinned patch set as part of the migration cost.
- The current registry exposes 79 call names (including aliases such as `song_url_v1` and `personal_fm_mode`). Rust's much larger module count reduces greenfield porting, but does not reduce the need to validate all 79 Atom contracts because the product protocol deliberately permits arbitrary named provider calls.

## Netease Rust Replacement Decision

- **Feasible, but not as a drop-in replacement and not advisable as a one-shot rewrite.** The safe seam is to retain the existing `callNetease(name, params)` facade, Core-owned SQLite session/cache/policy, and all Control contracts, while delegating individual provider operations to a pinned Atom-maintained Rust sidecar.
- Prefer a private stdio JSON-RPC sidecar (or, for a first spike only, loopback HTTP bound to `127.0.0.1`) over a new N-API addon or putting provider code into `audio-engine`. The stock server must not be shipped unchanged: its default `0.0.0.0` listener, missing cloud routes, generic path mapping, and current compatibility bugs do not meet Atom's boundary.
- Use a strangler migration: public read-only calls first; authenticated read calls; playback/download URLs and session mutation; playlist/favorite mutation; cloud/recognition/scrobble last. Keep the TypeScript implementation as an explicit per-method fallback during the migration, then remove it only after live parity. This is temporary migration control, not a second authority: session/cache/policy remain in Core and each API name has exactly one selected implementation.
- Do not switch the critical `song_url` path until Rust supports the exact current v1/xeapi behavior or equivalent live-account evidence proves eapi parity for VIP/SVIP and Diretta materialization. Do not drop `scrobble_v1`; port it or retain the current implementation.

## Effort Estimate (one experienced engineer)

- **Proof of concept, Linux only, public search/detail/lyrics plus one non-entitled URL:** 2–4 engineer-days. This proves process/serialization/build plumbing, not migration feasibility for the product.
- **Linux Core playback slice, preserving cookie/session and VIP URL semantics:** 8–12 engineer-days, assuming test credentials are available and no new provider anti-abuse behavior is discovered.
- **Full Linux Core Netease parity for the 79-name Atom surface:** 20–30 engineer-days (about 4–6 weeks). Includes an Atom Rust fork, explicit compatibility dispatch, xeapi/anonymous/device work, cloud route fixes, proxy-aware recognition, scrobble/NCM-BL port, contract tests, sidecar lifecycle, Core artifact staging, and live-account regression.
- **Production replacement across Linux Core plus Windows/macOS/Linux Desktop packaging:** 30–45 engineer-days (about 6–9 weeks). Cross-platform binary builds/signing/staging, Electron package lookup, shutdown/crash handling, and per-platform smoke add the remaining work.
- Estimate uncertainty is roughly ±35% because several acceptance items require a real account/VIP entitlement and the upstream provider protocol can change. If `ncm-api-rs` first gains proven xeapi, generic named dispatch, cloud server routes, and NCM-BL parity upstream, the full estimate can drop by roughly 8–12 days.

## Recommendation

- Do not prioritize the full replacement ahead of the roadmap's unfinished Netease playback acceptance. First finish/automate continuous-play and URL-refresh tests against the current known-good implementation; those tests become the migration oracle.
- If the motivation is memory, the measured sidecar saves little in the context of an already-running Node Core unless the current Netease implementation is shown to dominate memory; measure the existing periodic Core/app metrics before committing. If the motivation is maintainability/API breadth, a staged Rust adoption is more defensible, but Atom must budget ownership of a fork.

- §16 Settings gap is concrete: `src/stores/settings.ts::setSystem()` sends every `system.*` binding through `window.api.config.set()`. Desktop `config:set` owns mixed Core and Host side effects, while Web's facade maps the same generic API to `/config`; this creates transport parity without an ownership boundary.
- The first Settings convergence slice uses an explicit shared Core-setting ownership classifier plus a thin `settingsClient`/runtime-neutral main service. Shared UI mutations for Core-owned paths use that client; Host/Control-local paths remain on `window.api.config`. At that checkpoint Web's generic `/config` mutation rejected Core paths because tightening Desktop `config:set` would have raised business touches to 106. A later P4 consumer audit proved the Headless/Core HTTP `/config` GET/POST had no production, debug, or retained legacy consumer, so that generic HTTP surface is now removed entirely; Desktop `config:set` remains only a local Host/backup compatibility seam.
- Core Settings side effects that previously diverged between Desktop and Web are now centralized for the migrated paths: playback preload invalidation, normalization, EQ and fade changes are applied in the Core service. Dedicated output/cache-dir/download-dir/NowPlaying paths are intentionally excluded so their existing domain clients keep validation and lifecycle authority.
- `syncSystem()` is part of player initialization/recovery as well as Settings-page refresh, so replacing its full config read requires preserving Control-local onboarding/agreement and Host settings across reloads. A read split cannot simply make Web return defaults for non-Core fields without first defining their local persistence; the next consumer migration must avoid that regression.
- The Settings read split is now complete for production shared UI. `syncSystem()` reads the current Control snapshot and `settingsClient.getSnapshot()` together, then applies the Core snapshot last so Core-owned values cannot be shadowed by Control state. `CoreSettingsSnapshot` remains limited to player/library/lyric/localLyric/cache/download/streaming plus Core network/Netease-scrobble fields.
- Web no longer uses the Headless mixed `/config` snapshot. Its compatibility `ConfigApi` persists only `system.onboardingCompleted`, `system.agreedAgreementVersion`, and `system.uiZoom` in localStorage; all Core-owned paths and all other Host/Desktop scopes are rejected instead of silently creating fake state. Stale local entries outside that allowlist are ignored. UI Zoom is a real This-Control preference in Web and reapplies browser zoom on reload.
- Completing that boundary exposed a residual fake Host write: the shared FontConfig save path still wrote desktop/dynamic-island/taskbar lyric fonts even when those fields were hidden. Those writes now run only when the Desktop lyric capability exists.
- Web Settings hides Desktop-only system media/Discord/Last.fm/External API sections plus AI/MCP. Plugins are no longer hidden: the unique Core `pluginRegistry` now has a shared `pluginControl` service, `/plugins/*` routes, `pluginClient`, and `pluginStatus` Core event projection; Web exposes installed plugins and market management while filtering only the local script picker/import section.
- Desktop did not need a new `src/stores/plugins.ts` touch. The already-touched preload compatibility facade now forwards every Plugin business method except local-path install/native picker through `atom-core://control`, and filters plugin status from the shared `core:event`. This avoids a second registry/store and keeps the upstream business touch count at 105.
- Plugin projection now initializes during both Desktop and Web player startup, so plugin lyric/cover/menu fallback no longer depends on opening Settings first. The old non-picker `electron/main/ipc/plugin.ts` handlers remain legacy compatibility but have no production renderer callers through the preload facade.
- The remaining §16 Web reachability audit is now classified and implemented as Host/presentation capability rather than Core migration: Recognition uses `musicRecognition`; Cloud keeps provider-backed browse/play in Web while local upload uses `cloudUpload`; native OpenCC lyric conversion uses `nativeCjkTransform` and its setting is absent when unsupported.
- To add the Recognition/Cloud UI guards without growing the 105 business-touch budget, the previous per-category Web gating in `src/settings/categories/general.ts` and `appearance.ts` was moved into the already-touched schema aggregation seam, and both category files were restored byte-for-byte to upstream. Those two retired touches were exchanged for `NavSearch.vue` and `Cloud.vue`; touch audit remains 105 / 22 / 13.
- The existing `AGENTS.md` mixes durable engineering constraints with a stale upstream architecture snapshot. Suspect items already visible before the full roadmap comparison include the Windows/Git-Bash-only shell claim, IPC-only playback flow, a platform union that omits Qobuz/TIDAL, and language that still treats Headless/Core as merely hypothetical.
- The roadmap's durable product model is now Core-centric: Node Core owns database/settings/library/providers/playback/session/queue/policy/source resolution/cache/preload/recovery/output assignment, while Web and Desktop are Controls over one Core Protocol. The current `AGENTS.md` description of renderer → IPC → main playback and “Headless/Core may not become a domain” is therefore materially outdated.
- Durable release constraints worth retaining compactly are Node `>=24.18.0 <25` with reference `24.18.0`, Linux x86-64 Core Local Output through ALSA or Diretta, a Core build free of Electron/Desktop native dependencies, and a required SDK 149 gate for Diretta-branded Core releases.
- Source inspection confirms the roadmap model is implemented rather than aspirational: `shared/types/platform.ts` includes Qobuz/TIDAL, Desktop requests use `atom-core://control`, Desktop and Headless mount `buildCoreControlRoutes()`, Core runtime constants enforce Node `>=24.18.0 <25`, and the Core native/release scripts enforce `core-audio` plus Diretta SDK 149 provenance.
- Compression should keep operational invariants, not volatile inventories. Exact module lists, IPC diagrams, type unions, storage trees, test counts, accepted upstream commits, and phase completion belong in source or formal docs (`atom-roadmap`, `atom-development`, `types`, `build-flavors`, `core-deployment`, `upstream-sync`).
- The compressed `AGENTS.md` now encodes the Core/Control/Output authority model, frozen QQ/Kugou boundary, trusted-LAN product assumption, upstream Git model, SDK 149 release policy, strict Source Direct behavior, and durable engineering/memory rules. It removes roughly 39% of the prior word count while replacing outdated Electron/IPC, Windows-shell, platform-union, module-inventory, and storage-snapshot guidance.
- Comments, cache, download, filesystem browsing, and library file operations already had reusable Core-owned business seams; Web gaps were transport or Host-capability gaps, not reasons to create parallel domains.
- The combined §16 convergence baseline is Node 239/239, Web 66/66, Node/Web typecheck, ESLint, focused Prettier, `git diff --check`, touch audit 80 / 22 / 13, and a Desktop production build with native rebuild skipped.
- The ordinary and SDK-enabled Core artifact pipelines carry mutually consistent Diretta provenance. SDK-enabled artifacts record release 149; no-SDK artifacts record `diretta=false` and `direttaSdkRelease=null`.
- The first actual GitHub-hosted clean `Core System Gate` is complete, and hosted evidence remained green through `be96ad6` (run `33249130671`). The later `02d761d` and `a6df408` pushes both failed before any step or runner allocation because GitHub reported the same account payment / Actions spending-limit block across hosted jobs; this is external CI infrastructure and provides no code-failure evidence.
- Secure Diretta SDK provisioning is now an explicit release policy: a manual `Core Diretta Release Gate` runs only on a controlled self-hosted Ubuntu 24.04 x86-64 runner labeled `diretta-sdk-149`, with SDK 149 pre-provisioned read-only outside the checkout. The SDK is not stored in repository history, GitHub Secrets, Actions artifacts or release uploads. The `diretta-release` Environment exists with a `dev`-only deployment policy; the first remote SDK-enabled run is now blocked only on registering the trusted runner.
- Remote Qobuz/TIDAL acceptance still requires user-owned authentication. Physical DAC/front-panel bitstream confirmation remains a manual boundary.
- Network proxy configuration/testing and audio-output reinitialization are Core Domain behavior: Web now calls the same Core proxy test and `playerControl.reinitOutput()` path as Desktop rather than returning unsupported.
- The Netease embedded login BrowserWindow and installed-font enumeration are Control Host capabilities, not provider/Core auth behavior. The final Host-facade reachability audit also closed Web access to Desktop file explorer, host-save, updater/window initialization and desktop-lyric window subscriptions: Download file-location actions are hidden without `hostFileExplorer`, lyric-poster export uses `browserDownload`, and Desktop updater/window subscriptions are not initialized without their Host capabilities. Remaining no-op facade fields are compatibility shape rather than product capability.
- The shared `ControlAction` model remains evidence-driven and now covers Track; Collection (playlist/album/cloud/radio); Artist; and optional CoverList card presentation. Track right-click/row `...`, Collection/Artist primary+overflow actions, and Favorites cover-card unsubscribe all use the same semantic model/menu adapter while retaining the existing player/user/playlist execution paths; purely navigational cards remain click-only.
- Desktop's optional external API cannot be the internal Control transport because it is disabled by default and uses a different gated route set. The correct Desktop Core Protocol path is therefore the Electron-session-only `atom-core://control` Fetch scheme on the existing `persist:main` partition. Desktop and Headless Web mount one `buildCoreControlRoutes()` composition of the existing Headless router plus retained thin compat routes, so playback/session/output, Managed Provider, active Library, FFT, local HD cover and external lyric requests use the same path/payload contract without duplicating routes. Library cache URLs are projected only in Atom-owned Control code; `pickScanDir` / `pickCoverImage` remain Host actions and scan progress remains event transport. Managed Provider identity is one shared contract; QQ/Kugou retain only legacy compatibility IPC, embedded Netease login remains Host-only, and session push remains event transport. Remaining Player IPC is limited to tray/thumbar Host presentation (`syncPlayMode` / `syncLikeState`) and `onEvent`; request-style Player IPC no longer has active renderer callers. Renderer-facing Direct staging/materialization APIs and the dead renderer Direct preload result/generation state have been removed completely; Direct materialization, staging and gapless boundary commit remain Core-only. Event transport is the next convergence slice.

## Git Decision
